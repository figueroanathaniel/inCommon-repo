Check every claim in it against the files, not against memory. At least:
  a. The deploy folder is deploy/v6.4/, the value of <current> under "Current

  b. The wiring's 3D view is app/hd-scene.js (global HDScene). The chart is
     app/chart-scene.js, the Cycle Audit app/cycle-scene.js, close bodies
     app/body-globes.js, flight app/flight.js. Name each by its own file.
  c. The scenes compute nothing. Each draws a model the application builds
     from the same calculation the 2D view reads: _csModel from placedRows,
     natalAspects() and CAT_COLOR; _hsModel from hdChart(); the Cycle Audit
     from cycleSceneModel(). The one position a scene asks for itself comes
     through the app's own lonOf() (opts.lonAt). Anything in the document that
     has a scene calculate positions, gates or chart state is wrong. CLAUDE.md:
     "The natal chart is drawn three ways", "The wiring is drawn three ways",
     "The Cycle Audit is drawn four ways".
  d. Nothing in the browser talks to Supabase except app/incommon-cloud.js.
     A scene, a renderer or an engine module never holds a client.
  e. Remove the proposed direct write to oracle_readings. That table is
     written only by the Oracle edge function with the service role.
     server/oracle/schema.sql gives app users one policy, "read own oracle
     readings", and on purpose no insert, update or delete policy, so a client
     write is refused by row level security, and the daily limit counts those
     rows, so a reader who could write them could defeat it. A reading reaches
     the page through oracleRead() in incommon-cloud.js and is kept on the
     device by oracleKeep(). If the document needs a reading in the engine,
     it takes it from the application, never from the database.
  f. No dash of any kind (CLAUDE.md "Zero em dash"), "astral body" in prose,
     and no "bodygraph" in a heading (check-competitor-surface.js walks docs/).
